## Completed Tasks

### cli_concurrency_guard — all 7 steps (2026-02-04)
Added ECS concurrency guard to `silver catchup` and `silver maintain` CLI commands:
1. Added `--skip-if-concurrent` flag to `silver catchup` in silver.py, following the
   same pattern as Bronze `backfill catchup`.
2. Entity-scoped concurrency filter: `silver-{platform}-{entity}` (e.g. `silver-polymarket-trades`)
   so different entity types CAN run concurrently but the SAME entity type CANNOT overlap.
3. `should_skip_concurrent()` is the ABSOLUTE FIRST operation in `_run_catchup()` — placed
   before all imports, S3Client construction, state store load, manifest discovery, and
   markets reference load. A skipped invocation costs only ECS cold start + one API call.
4. On concurrent detection: prints info message (not warning) and exits code 0.
5. Added `--skip-if-concurrent` to `silver maintain` command as well, with filter
   string `silver-maintain`. Guard runs before any Glue/catalog operations.
6. Added 7 unit tests in test_silver_cli.py:
   - TestCatchupConcurrencyGuard: guard returns True exits cleanly, guard returns
     False proceeds, entity-scoped filter verified, without flag guard not called
   - TestMaintainConcurrencyGuard: guard returns True exits cleanly, guard returns
     False proceeds, without flag guard not called
7. mypy and ruff: no new errors introduced (all pre-existing). 1281 tests passing.

### catchup_noop_optimization — steps 1, 2, 3 (2026-02-04)
Verified from code committed in 3d03e41:
1. Audited _run_catchup() no-op hot path: state_store.load() → discover_manifests()
   → filter already-processed → early-return "Silver is up to date". Markets reference,
   Glue catalog, and chunked processing are NOT loaded on the no-op path. Architecture
   is correct for near-continuous scheduling.
2. Confirmed markets reference loading (the most expensive startup operation for trades)
   is gated behind the "All manifests already processed" early-return check at silver.py
   lines 629-650. No-op runs never touch it.
3. Added `silver_catchup_noop` structured log event at both no-op exit points in
   _run_catchup() (silver.py). Uses structlog via `get_logger(__name__)` for CloudWatch-
   compatible JSON output. Two exit paths instrumented:
   - `reason=no_manifests`: when discover_manifests() returns empty — emits platform,
     entity, start_date, end_date, duration_s
   - `reason=all_processed`: when all discovered manifests are already in state store —
     additionally emits manifests_discovered count
   Timer starts with `time.monotonic()` immediately after lazy imports (right after the
   concurrency guard, before S3Client construction), so duration_s captures the full
   cost of a no-op invocation: state store load + manifest discovery + filtering.
   Added 3 unit tests in TestCatchupNoopLogging:
   - test_noop_log_emitted_when_no_manifests_found: verifies event name, fields, reason
   - test_noop_log_emitted_when_all_manifests_processed: verifies manifests_discovered
   - test_noop_log_not_emitted_when_manifests_to_process: negative case
   Step 4 (lightweight pre-check) deferred per PRD — implement only if manifest discovery
   takes >5s, to be measured during deployment_and_validation.
   mypy and ruff: no new errors introduced. 1314 tests passing (34 silver CLI tests).

## Notes

- This sprint implements near-continuous Silver processing via EventBridge schedules.
- Key design decisions:
  - Trades: every 10 min (Bronze order_filled ingests every 5 min, so ~2 batches per Silver cycle)
  - Catalog (markets, events): every 30 min (Bronze ingests hourly)
  - Kalshi: schedules created but DISABLED until data pipeline is activated
  - Maintenance: daily compact at 04:00 UTC, weekly full at Sunday 04:00 UTC
  - Concurrency guard is per-entity (trades can run concurrently with markets, but not two trades runs)
- Architecture already supports this (from sprint 10 + 3d03e41): independent run_ids, per-manifest
  state tracking, fast append for stream entities, memory-safe chunked processing.
- Expected cost profile: ~$0.50-1.00/day for schedule invocations (mostly no-op exits at 0.25 vCPU)
  plus actual processing costs proportional to data volume.
