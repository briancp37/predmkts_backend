### quality_checks_catalog_entities (2026-02-03)
All 5 steps completed:
1. Analyzed timestamp_range check behavior: catalog entity snapshots (markets,
   events) contain records with timestamps spanning years (2023-2026 for a
   dt=2026-02-03 snapshot). The default ±1 day tolerance window in
   TimestampRangeCheck rejects ~97% of these records, making quality checks
   unusable without --skip-quality-checks.
2. Designed entity-type-aware approach: added CATALOG_ENTITIES frozenset
   containing {"markets", "events"} in quality.py. Catalog entities skip the
   timestamp_range check entirely since their timestamps naturally span years
   and the check is not meaningful for snapshot data.
3. Updated checks_for_entity() in quality.py: the TimestampRangeCheck is now
   only added when `entity not in CATALOG_ENTITIES`. This is a one-line
   conditional change that preserves all other checks (non_null, uniqueness,
   referential) for catalog entities.
4. Verified stream entities (trades, order_filled) retain strict ±1 day
   timestamp_range checks — no behavior change for stream entities.
5. Added 8 new tests in test_silver_quality.py:
   - TestChecksForEntity: test_catalog_entity_no_timestamp_range,

### silver_trades_processing — steps 1, 2, 6 (2026-02-03)
3 of 6 steps completed (steps 1, 2, 6 — the code/architecture steps):
1. Verified PolymarketTradesNormalizer wiring: get_normalizer() returns a bare
   instance with _lookup=None. Calling normalize_batch() raises NormalizationError
   because derive_trade() accesses self.lookup which raises when None. This was
   the critical blocker for all Silver trades processing.
2. Implemented automatic MarketsReferenceLookup loading in processor.py:
   - After dedup and before normalization, process_manifest() checks if the
     normalizer is an instance of PolymarketTradesNormalizer.
   - If so, calls load_markets_reference(s3_client, end_date=dt) to build the
     token-to-market lookup from Bronze polymarket/markets manifests.
   - Injects the lookup via normalizer.set_lookup(lookup).
   - The end_date parameter scopes the lookup to markets available up to the
     trade date being processed.
   - Structured logging at both "loading_markets_reference" and
     "markets_reference_loaded" events with coverage stats.
3. Edge case handling (step 6):
   - If load_markets_reference() raises an exception (e.g., S3 unavailable),
     it's caught and re-raised as ProcessingError with a clear message.
   - If the lookup is empty (no Bronze markets data found), raises
     ProcessingError with guidance to ingest markets first.
   - Individual order_filled records that fail token ID lookup are handled by
     the existing normalize_batch() skip-on-failure behavior — logged as
     warnings and skipped, not fatal.

Added 6 new tests in test_silver_processor.py (TestMarketsReferenceLookupAutoLoad):

### continuous_ingestion_architecture (2026-02-03)
All 7 steps completed:
1. Documented current limitation: order_filled catchup used date-scoped backfill
   (find latest date, backfill missing days). This meant: (a) if today's data was
   already ingested, catchup skipped it even though new records arrived; (b) Silver
   used select_snapshot_and_deltas() which for stream entities picked only the
   latest manifest per day, dropping earlier independent ingestion batches.
2. Designed new model: order_filled catchup now uses incremental timestamp-based
   ingestion. Each invocation finds the latest timestamp from existing manifests
   and fetches only records newer than that timestamp into today's dt partition
   with a fresh run_id.
3. order_filled already generated a new run_id per invocation (via RunContext()).
   The key change was in the catchup CLI — switching from date-scoped backfill
   to incremental timestamp-based mode using find_latest_timestamp().
4. Manifest semantics are already self-contained per run_id. Each catchup produces
   its own manifest under a unique run_id directory, making them independently
   processable.
5. Updated Silver processor's manifest selection: added select_manifests_for_day()
   in discovery.py which is entity-type-aware. Stream entities (trades,
   order_filled) process ALL manifests per day as independent batches. Catalog
   entities (markets, events) continue using snapshot-supersedes-delta logic.
   Added CATALOG_ENTITIES frozenset to discovery.py.
6. Silver state store already tracks by run_id (not per-day), so each manifest
   from each catchup invocation is independently trackable. No change needed.
7. Cross-manifest dedup is handled by the existing Iceberg merge/upsert with
   dedup keys. Records appearing in overlapping ingestion windows are deduplicated
   at the Iceberg level during merge_to_iceberg().

Files changed:
   - src/prediction_data/cli/main.py: order_filled catchup branch uses
     find_latest_timestamp() + ingest_order_filled(since_timestamp=...)
   - src/prediction_data/silver/discovery.py: added CATALOG_ENTITIES frozenset
     and select_manifests_for_day() function
   - src/prediction_data/cli/silver.py: replaced select_snapshot_and_deltas()

## Blockers/Issues

## Notes

- This sprint was created after the first live Silver deployment revealed critical bugs
  and architectural gaps in the Bronze → Silver pipeline.
- Key issues discovered during deployment:
  1. decompress_jsonl used splitlines() which breaks on U+2028 Unicode line separators
     embedded in API data (e.g., Polymarket market question fields)
  2. Normalizers expected snake_case fields but Gamma API returns camelCase
  3. skip_quality_checks CLI flag was defined but never wired to the processor
  4. timestamp_range quality check rejects 97% of catalog entity records (full snapshots
     contain records with timestamps spanning years, not scoped to one day)
  5. Current ingestion model (one run_id per day, overwritten manifest) prevents
     continuous Silver processing — once Silver processes a manifest, it marks it done
     and ignores subsequent data added to the same run_id
